# Data model (Phase 3 implementation)

PostgreSQL is the authoritative application metadata database. Actual video bytes are stored outside PostgreSQL using local/file storage for MVP. No model contains a binary video field. Footage persists a provider and opaque `storage_key`, never a public URL or constructed filesystem path. Database IDs are UUIDs; Django timestamps use timezone-aware UTC (`USE_TZ=True`). Foreign keys generally use `PROTECT` for historical/audit-sensitive records; audit actor uses `SET_NULL`.

## Phase 3 close-out verification

The domain test suite is discovered by Django and passes locally with the explicit test settings, which use an isolated in-memory SQLite database. This is not PostgreSQL validation. On 2026-10-04, live PostgreSQL migration execution, schema/constraint/index introspection, PostgreSQL-backed tests, and seed idempotency could not be run because Docker Compose was unavailable and the host PostgreSQL connection could not be attributed to this project's Compose service. Consequently, this document describes the intended/model-migration schema; it does not claim live PostgreSQL confirmation. See [PostgreSQL close-out verification](postgresql-verification.md).

## Model-validation boundary

Database constraints protect same-row invariants (positive capacity/duration/attempt bounds, enumerated states, uniqueness, valid intervals, required stored reference, confidence ranges). `Model.clean()` protects cross-row rules that a conventional FK/check cannot express: same-institution assignments, lecture/timetable context, camera/classroom match, and analytics provenance. Django does not call `full_clean()` on every `save()`; application use cases must call validation before persistence. Scheduling overlap/collision policy remains open and is not enforced by Phase 3.

## Cross-module ownership and deletion

Each Django app owns its models and migrations. Other apps may reference public model relations but must not write another app's tables directly from unrelated code. `PROTECT` prevents accidental deletion of source records needed to understand historical footage, jobs, observations, and reports. Retention and coordinated external-byte deletion remain future policy decisions.

## Deferred or unresolved data decisions

- Indicator scales, formulae, thresholds, and aggregation policy await CV validation and teacher review; values are stored with explicit units and provenance without imposing a 0–100 scale.
- Timetable overlap rules and lecture creation/assignment workflow remain open (ADR-013).
- Camera source details must remain non-secret references; approved secret-management integration and actual CCTV provider are future work.
- Global email uniqueness is selected to meet Django's unique email login identity. Supporting the same email in multiple institutions would require an explicit identity/tenant login design.
- LectureSummary was required as a persisted model for this phase although the original proposal derived summary from a report. It is versioned by analytics run and is a projection, not a second source of truth (ADR-022).
