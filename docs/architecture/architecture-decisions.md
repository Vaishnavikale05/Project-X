# Architecture decisions

Status labels: **Accepted** means baseline for planning; **Open** needs human/stakeholder input before implementation.

| ID | Decision | Status / rationale |
|---|---|---|
| ADR-001 | Use a Django/DRF modular monolith for core application workflows. | Accepted. Keeps transaction and deployment complexity modest while preserving logical module boundaries. |
| ADR-002 | Isolate CV processing behind a versioned Python structured contract; do not place CV in views. | Accepted. Allows separate worker/runtime later without prematurely requiring a network microservice. |
| ADR-003 | Keep actual video bytes in local/file storage for MVP; PostgreSQL stores metadata and opaque references. | Accepted. Supports MVP while preserving a replaceable adapter. |
| ADR-004 | Use Redis/Celery for asynchronous processing and persisted processing lifecycle in PostgreSQL. | Accepted. Media processing is long-running and must not block HTTP. |
| ADR-005 | Use `FootageProvider` for sample files now and future approved CCTV/NVR/VMS access later. | Accepted. Actual source technology and authorization are unknown. |
| ADR-006 | MVP roles are ADMIN and TEACHER; enforce institution and object scope server-side. | Accepted baseline. Exact account provisioning and teacher-to-lecture assignment policy need confirmation. |
| ADR-007 | No student identity recognition; use per-run pseudonymous tracks and class-level analytics. | Accepted for MVP. Privacy-preserving baseline. |
| ADR-008 | Analytics formulas are explicit/versioned; recommendation rules are deterministic and traceable. | Accepted. LLM may optionally phrase approved content later but cannot create metrics. |
| ADR-009 | Domain IDs use UUIDs; timestamps are timezone-aware UTC; API is `/api/v1`. | Accepted design convention, subject to team review. |
| ADR-010 | CV segmentation/model family and metrics are not fixed beyond candidate tools. | Open. Evaluate representative authorized data, camera conditions, hardware, accuracy/coverage, and licensing before selection. |
| ADR-011 | Centralize authentication in the accounts boundary using SimpleJWT access/refresh tokens: 5-minute HS256 access JWTs and 12-hour rotating refresh JWTs. Keep access only in React memory; set refresh in an HttpOnly, SameSite=Lax cookie scoped to `/api/v1/auth/`; require Django CSRF validation on login/refresh/logout. Store signing key in environment, distinct and mandatory in production. Blacklist rotated/logout refresh tokens in PostgreSQL; allow outstanding access tokens to expire within five minutes. | Accepted for Phase 4. This meets the API-first SPA contract while avoiding long-lived refresh tokens in browser-readable storage. Same-origin SPA/API is the baseline; deployment-specific CORS/proxy topology must be reviewed before release. Refresh lifetime is a rolling 12-hour inactivity limit, with no absolute lifetime cap. Django/JWT role claims are not trusted; current role/activity are loaded from the user row. |
| ADR-012 | Local storage root, quota, backup, retention, and deletion policy. | Open. Requires deployment capacity and institutional privacy/legal review. |
| ADR-013 | Timetable collision semantics, lecture creation source, and teacher assignment model. | Open. Confirm academic workflow before schema finalization. |
| ADR-014 | Numeric performance, throughput, availability, recovery, and data-retention targets. | Open. Set from workload and operational requirements. |
| ADR-015 | Report export formats, recommendation wording, and indicator thresholds. | Open. Require teacher stakeholder review and CV validation evidence. |
| ADR-016 | Baseline development toolchain: Python 3.12, Django 5.2 LTS, DRF 3.18, Celery 5.6, React 19, TypeScript 5.9, Vite 8, Node 22, PostgreSQL 17, Redis 7; use GitHub Actions CI. | Accepted for Phase 2. Exact direct package versions and resolved locks are checked in. Review upgrades through CI; production image patch/digest pinning remains open for Phase 14. |
| ADR-017 | Use `backend/src/project_x_backend` for the Django modular monolith, `frontend/src` for React, and an independent `ai/src/project_x_ai` Python package. | Accepted for repository organization. CV package has no Django dependency; Compose liveness does not make it a business microservice. |
| ADR-018 | Pin direct Python dependencies in separate backend/AI requirements files; pin frontend dependencies and commit npm lockfile. | Accepted for Phase 2. CI uses exact lock/install commands; transitive Python pinning is a future lockfile/tooling improvement if reproducibility review requires it. |
| ADR-019 | Provide anonymous `/api/v1/health` for sanitized PostgreSQL/Redis readiness; require JWT authentication by default on protected DRF routes. Keep OpenAPI schema/docs public in development. | Accepted. Health, CSRF bootstrap, login, refresh, and logout explicitly opt out of bearer auth; refresh-cookie operations require CSRF. Business object-scope checks are enforced by each resource API; infrastructure scoping is implemented in Phase 5. |
| ADR-020 | Implement generic local filesystem storage behind `StorageProvider`; persist generated opaque keys and compute size/checksum metadata. | Accepted. No footage/domain policy is in the adapter; future object stores implement the same port. |
| ADR-021 | Define `FootageSource` plus local sample and future college source protocols. | Accepted. Neither an ingestion workflow nor actual college integration is part of Phase 2. |
| ADR-022 | Persist `LectureSummary` as a projection of one exact `AnalyticsRun`. | Accepted for Phase 3 because the implementation requirements explicitly require persistent lecture-level summary data. Each analytics run has at most one summary; the run's `IndicatorAggregate` rows remain the metric source of truth, and new runs produce new summaries. |
| ADR-023 | Require globally unique, case-insensitive email identity for the custom Django User model. | Accepted for Phase 3. Django's email `USERNAME_FIELD` needs a unique identity; storing one global identity avoids ambiguous login across institutions. Institution-scoped user email duplication is not supported. Revisit only if a future multi-tenant login/identity design explicitly requires it. |
| ADR-024 | Store `CVRun` and `CVObservation` in the backend processing domain; store `AnalyticsRun` and `IndicatorAggregate` in analytics. | Accepted for Phase 3 to preserve ownership: processing owns structured CV output and provenance; analytics consumes it through explicit foreign-key relationships without mixing observable signals with derived indicators. |
| ADR-025 | Centralize coarse role checks in reusable DRF permission classes and defer authentication audit-event writes until Operations/Audit integration. | Accepted for Phase 4. `IsAdminRole`, `IsTeacherRole`, and `IsAdminOrTeacherRole` avoid scattered view checks; Phase 5 infrastructure APIs now add institution-scope policies. Lecture assignment policies remain for lecture APIs. Audit failure events need retention and abuse-volume policy; do not persist credentials or add per-failure writes before that policy is defined. |
| ADR-026 | Preserve fast SQLite/locmem unit tests and add a separate explicit PostgreSQL/Redis integration-test settings module. | Accepted for Phase 4 validation. Pytest and the explicit Django fast-test command use isolated local resources. `settings.test_postgres` restores environment-configured PostgreSQL and Redis, fails closed rather than falling back, and runs against a disposable Django test database. This keeps routine tests fast while making database/cache integration verifiable against the Compose services without touching seeded application data. |
| ADR-027 | Provision Institution outside institution-scoped APIs; globally case-insensitive unique internal camera codes; require explicit child-first deactivation; audit successful infrastructure mutations with redacted field-name metadata. | Accepted for Phase 5. Institution-scoped ADMIN cannot create tenants. Existing classroom uniqueness remains per-institution, while camera identifier constraint is global. Active children block parent deactivation; there are no cascades or hard deletes. Transactional audit stores actor/action/resource/request ID/changed field names, never request values or secrets. |
